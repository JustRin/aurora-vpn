# Veil — свой туннель Aurora VPN

Снаружи Veil — это обычный Chrome на обычном сайте. На 443 стоит Caddy с
настоящим сайтом и сертификатом Let's Encrypt. Клиент открывает TLS 1.3 с
отпечатком Chrome на домен этого сайта, договаривается о HTTP/2 и держит одно
соединение, как открытая вкладка. Каждое соединение, которое идёт через
туннель, — это отдельный POST внутри него. Кто пришёл без жетона, получает
сайт.

## Что видит ТСПУ и что с этим сделано

| Признак, по которому ловят | Как у Veil |
|---|---|
| SNI не сходится с IP (icloud.com на хостинге) | SNI — ваш домен, сертификат выдан ему и стоит на этом же IP |
| Активная проба отвечает не как сайт (VLESS-TLS :2083 рвал GET) | Любой запрос без жетона получает настоящий сайт от Caddy; путь туннеля без жетона — пустой 404, как любой несуществующий адрес |
| Отпечаток клиента | JA4 совпадает с живым Chromium 2026 (`t13d1516h2_8daaf6152771_806a8c22fdea`, сверено захватом на NL): те же шифры, расширения, подписи с ML-DSA, группа X25519MLKEM768 объявлена — но без самого ключа, поэтому hello 510 Б в одном сегменте (ТСПУ режет второй сегмент hello до хостинга). Цена — hello меньше, чем у Chrome (1,8 КБ) |
| Первые записи после рукопожатия | Как у браузера: предисловие h2 отдельной записью 87 Б, затем `GET /` с Client Hints, ответ, и только потом запросы туннеля |
| Отпечаток сервера | TLS отдаёт Caddy (Go), а не самодельный сервер. HTTP/3 выключен (браузеры и Veil одинаково идут по TCP), `curves x25519 …` — иначе Caddy ответил бы HRR на PQ-группу без ключа |
| «TLS в TLS» по размерам записей | Первые 8 записей каждого потока набиваются до 900–1400 байт; кадры h2 склеиваются до flush, поэтому записи разного размера, как у браузера |
| Одна многочасовая сессия с ровным потоком | Соединение живёт 4–12 минут (случайно), потом новое; каждое начинается с `GET /`, как загрузка страницы |
| Повтор перехваченного запроса | Жетон: nonce + время + HMAC, повтор nonce отвергается, окно ±5 минут |
| Доступ к расшифрованному потоку на фронте или реле | Внутри TLS ещё ChaCha20-Poly1305 с ключом на каждый поток: Caddy, CDN и реле видят только шифротекст |

Честно о пределах. Протокол убирает признаки самого протокола. Но IP в
2026 году банят и по поведению: десятки абонентов из РФ на одном
иностранном хостинговом IP круглые сутки. Против этого протокол бессилен,
помогает только эксплуатация (см. ниже).

## Сборка сервера (с Windows)

```bash
rustup target add x86_64-unknown-linux-musl
cd veil && cargo build --release --target x86_64-unknown-linux-musl
```

Получится статический бинарник `target/x86_64-unknown-linux-musl/release/veil-server`
(≈1,3 МБ, без зависимостей). Линковщик `rust-lld` задан в `.cargo/config.toml`.

## Установка

Нужны свежий VPS и **новый домен** (не засвеченный `scmanga.site`) с A-записью
на этот VPS.

```bash
scp target/x86_64-unknown-linux-musl/release/veil-server deploy/* root@СЕРВЕР:/root/veil/
ssh root@СЕРВЕР 'cd /root/veil && bash install.sh --domain ДОМЕН --site ./site --install-caddy'
```

`install.sh` ставит `veil-server` под systemd, создаёт `/etc/veil/config.json`
со случайным путём и паролем администратора, ставит Caddy и пишет Caddyfile.
В конце печатает ссылку `veil://…`. Папка `site` — сайт-маска, например из
генератора `Desktop/scmanga-site`.

Друзья добавляются без перезапуска, конфиг перечитывается за 30 секунд:

```bash
veil-server adduser -c /etc/veil/config.json --host ДОМЕН имя
```

Каждые 10 минут в журнале появляется сводка по пользователям
(`journalctl -u veil`). Отказы входа на путь туннеля пишутся с IP из
X-Forwarded-For. Если такие отказы появились, путь кто-то нашёл.

## Подписки 3x-ui с Veil

`veil-server` встаёт посредником между клиентами и подпиской 3x-ui
(`src/subs.rs`). Клиент запрашивает `https://ДОМЕН/subs/<subId>`, Caddy
передаёт запрос в `veil-server`, тот забирает подписку панели и дописывает
в конец ссылку `veil://`. Заголовки трафика, срока и интервала обновления
сохраняются.

- **Пароль Veil** выводится из subId и секрета сервера (раздел `subscription`
  в config.json). Вносить людей в конфиг Veil не нужно.
- **Источник правды — панель.** Раз в 30 минут `veil-server` сверяет выданные
  subId с 3x-ui. Если панель больше не отдаёт подписку (клиент отключён,
  удалён, кончился срок), доступ к Veil снимается.
- **Только Aurora.** Ссылку Veil получают только клиенты с User-Agent
  `Aurora-VPN` (настройка `clients`). Happ, v2rayNG и прочие видят подписку
  панели без изменений.
- **К панели `veil-server` ходит по HTTP.** Если подписка 3x-ui на TLS, мостом
  служит Caddy: `http://:2097` с `bind 127.0.0.1` → `https://127.0.0.1:2096`.
  `install.sh --xui` ставит всё это сам.

Чтобы и старые ссылки `https://ДОМЕН:2096/subs/<subId>` получали Veil, в
панели в настройках подписки укажите «Listen IP» `127.0.0.1` (порт и
сертификат оставьте). Тогда публичный 2096 освободится для Caddy. В поле
«Subscription URI» стоит указать `https://ДОМЕН/subs/`, чтобы панель
показывала новым клиентам ссылку на 443.

## Эксплуатация: что важнее протокола

0. **Российские сервисы не должны видеть IP сервера.** С апреля 2026 крупные
   платформы (Сбер, Яндекс, VK, Ozon, Wildberries, Avito, X5) обязаны
   выявлять VPN по методике Минцифры. Если телефон шлёт их трафик через
   туннель, они видят IP сервера как адрес российского аккаунта. 02.11 так и
   было: перед блоком NL один телефон 14 часов гнал через него VK, Яндекс,
   Ozon и RuStore. Поэтому:
   - в Aurora «Россия напрямую» включена по умолчанию (и разово у всех
     существующих пользователей), встроенный список доменов работает даже
     без скачанных гео-наборов, а на Android российские приложения
     целиком идут мимо туннеля;
   - `veil-server` с `"block_ru": true` (по умолчанию) не выпускает наружу
     российские домены и сети из `/etc/veil/ru-cidr.txt` (ipdeny, обновление
     раз в неделю). Первый отказ за 10 минут сразу пишется в журнал с именем
     пользователя: так видно, у кого из друзей защита выключена;
   - на серверах с 3x-ui то же делает `STRICT=1 bash apply-ru-block.sh` из
     `Desktop/scmanga-site/deploy`.
1. **На IP не должно быть ничего, кроме сайта.** Без Hysteria, REALITY,
   панели 3x-ui, Postgres и MTProto. Снаружи открыты только 22, 80 и 443.
   Hysteria по UDP на том же IP выдаёт его сразу.
2. **Новый домен на новый IP.** Ссылки на домен, а не на IP. Старый домен,
   который ходил за забаненными IP, не переносить.
3. **Реле в РФ.** Самая сильная мера: клиенты ходят на российский VPS (Yandex
   Cloud, Selectel, VK Cloud), он пересылает TCP 80/443 на NL. Домен
   указывает на реле. ТСПУ видит TLS к российскому дата-центру, а связь
   РФ→NL идёт между дата-центрами. Так переживается и режим белых списков у
   мобильных операторов, если хостер реле в белом списке. Пример для
   nftables на реле (NL_IP — адрес сервера Veil):
   ```
   nft add table ip relay
   nft add chain ip relay pre '{ type nat hook prerouting priority -100; }'
   nft add chain ip relay post '{ type nat hook postrouting priority 100; }'
   nft add rule ip relay pre tcp dport '{ 80, 443 }' dnat to NL_IP
   nft add rule ip relay post ip daddr NL_IP masquerade
   sysctl -w net.ipv4.ip_forward=1
   ```
4. **Несколько узлов и немного людей на каждом.** Два-три сервера с разными
   доменами в подписке. Блок одного не роняет остальных, а 30 человек на
   одном IP — самый заметный поведенческий признак.
5. **Не менять SNI на ходу.** SNI должен совпадать с сертификатом на этом IP.
   Чужие и меняющиеся SNI — ровно то, что ТСПУ сверяет с IP.

```
veil://ПАРОЛЬ@ДОМЕН:443?path=%2Fapi%2Fv1%2Fsync%2Fxxxx&sni=ДОМЕН&fp=chrome#Имя
```

## Где работает клиент

- **Windows:** на встроенном движке Aura. Выбранный Veil-сервер включает
  Aura на это подключение сам.
- **Android, Linux, macOS:** sing-box и libbox Veil не знают, поэтому узлы везёт движок Aura внутри
  процесса приложения, а sing-box ходит к нему через loopback-SOCKS
  (`src-tauri/src/core/veil.rs`). Входы закрыты паролем сессии: на телефоне
  127.0.0.1 общий для всех приложений. Сокеты движка выводятся из VPN через
  `VpnService.protect`, имя сервера он резолвит сам через DNS «напрямую».
  Туннель, поднятый виджетом или плиткой без открытого приложения, Veil не
  повезёт, пока приложение не откроют: движок живёт в Rust-части.
  На Linux и macOS `protect` не нужен: свой дозвон движка до сервера sing-box
  выпускает мимо туннеля по адресу сервера.

## Проверено

- Юнит-тесты кодека, жетона и адресов. Сквозные тесты в процессе (`cargo test`):
  5 МБ через один поток, 150 параллельных потоков, UDP, неверный пароль, пустой
  404 для проб.
- Стенд: движок aura → TLS-фронт с h2 (Node вместо Caddy) → veil-server →
  интернет. HTTPS, UDP-DNS, скорость 100 МБ равна прямой (~40 МБ/с, упор в
  канал). Память: движок 12 МБ, сервер 9,5 МБ.
- Linux-бинарник запускался на NL (ядро 6.8): `init`, `adduser`, `run`.
- Не проверено: живой Caddy и nginx перед veil-server, работа из РФ.
